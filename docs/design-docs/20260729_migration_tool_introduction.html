1. 背景と目的

現状、DB スキーマは scripts/database/ddl/schema.sql の単一ファイルで管理されており、 変更履歴・適用状況・環境間の一貫性を保証する仕組みが存在しない。 2025-11 に発生した本番のスキーマドリフト（ops.shift_plans の UNIQUE 制約欠落）は、 起動時ワークアラウンド（ensureShiftPlansUniqueConstraint.js）で暫定対処されているが、 これは根本解決ではない。

本設計では、Node.js + PostgreSQL + Railway という技術スタックに適合するマイグレーション管理ツールを選定し、 既存 schema.sql を「初期状態のスナップショット」として取り込みつつ、 以降のスキーマ変更を追跡可能・再現可能・レビュー可能にするための移行計画と CI 統合方針を定める。

本 Issue のスコープ:
  • ツール比較・選定の根拠を明文化する
  • 移行手順とディレクトリ構成を設計する
  • CI 統合ジョブを設計する
本 Issue のスコープ外:
  • 実際のツール導入・依存追加・初期マイグレーションの生成（別 Issue で実装）
  • staging / production への実適用

2-3. 現状の問題点

  • 変更履歴が不在: schema.sql は Git 履歴で追えるが、環境ごとに「どの状態が適用済みか」を機械的に判定できない。
  • 本番への適用がヒトの手作業: Railway Console での手動 SQL 実行に依存しており、実行漏れ・実行順序ズレのリスクがある（実際に ops.shift_plans のドリフトが発生）。
  • ロールバック不可: 前方への変更しか記述されておらず、失敗時の巻き戻し手順が定義されていない。
  • staging / production の乖離検出不能: 環境間でスキーマが揃っているかをコードから確認する術がない。
  • 起動時マイグレーションは根本解決ではない: ワークアラウンドが増え続けると server.js の起動シーケンスが肥大化・複雑化する。

4. 推奨ツールと根拠

推奨: node-pg-migrate

4-1. 選定理由

  1. 技術スタック整合性: 本プロジェクトは Node.js ESM + pg ドライバで完結している。 node-pg-migrate は同じ pg ドライバをそのまま使うため、 接続設定（DATABASE_URL）を含めた既存資産を再利用できる。追加ランタイム（JRE 等）は不要。
  2. 複数スキーマとの相性: core / hr / ops / analytics の 4 スキーマ横断的な DDL を生 SQL（pgm.sql()）で自由に記述でき、DSL に閉じ込められない。 既存の schema.sql（968 行）をほぼそのまま初期マイグレーションに取り込める。
  3. ロールバック標準サポート: up / down が対でファイル化されるため、失敗時の巻き戻しが CLI 一発で可能（node-pg-migrate down）。 Flyway OSS 版と比較した優位点。
  4. CI 適合: npx node-pg-migrate up --dry-run で未適用マイグレーションの検出、 up でトランザクション適用ができ、GitHub Actions のシンプルな Postgres サービスコンテナで検証できる。
  5. メンテナンス継続性: 2026-07 時点で GitHub 上の活動が継続しており、後方互換性の維持ポリシーも明文化されている。
  6. 学習コスト最小化: shift M層は Node.js + 生 SQL の運用に慣れており、Knex QueryBuilder の DSL を新規に習得する必要がない。

4-2. 却下理由（他候補）

  • db-migrate: 汎用 RDB 対応で PG 特化機能が弱く、メンテ活性が低下傾向。ESM 対応も限定的。
  • Knex (migrations): Knex 本体の QueryBuilder を使わず migrations だけ利用するのは責務のミスマッチ。生 SQL 中心の運用と噛み合わない。
  • Flyway: Java ランタイムの持ち込みが Railway・GitHub Actions 両方で追加コストになる。Undo が有償版限定で down が事実上使えない。純 SQL 志向は魅力だが、ロールバック不能の運用リスクが上回る。

5. 移行計画（既存 schema.sql の取り込み）

5-1. 基本方針

既存 schema.sql（968 行）を 初期マイグレーション 1 本にまるごと取り込む（"baseline" 方式）。 過去の変更履歴を細分化して再現する必要はなく、 現在の staging / production のスキーマ状態を「バージョン 0000 = ベースライン」とみなす。

5-2. 段階

Phase 0: 準備（本 Issue の続きの実装 Issue）

  • backend/package.json に node-pg-migrate を devDependencies として追加。
  • backend/package.json の scripts に以下を追加: 
    "db:migrate:up": "node-pg-migrate up -m ../scripts/database/migrations",
"db:migrate:down": "node-pg-migrate down -m ../scripts/database/migrations",
"db:migrate:create": "node-pg-migrate create -m ../scripts/database/migrations",
"db:migrate:status": "node-pg-migrate up --dry-run -m ../scripts/database/migrations"
  • 設定ファイル backend/.node-pg-migraterc.json を追加: 
    {
  "migrations-dir": "../scripts/database/migrations",
  "migrations-table": "pgmigrations",
  "migration-file-language": "js",
  "database-url-var": "DATABASE_URL",
  "check-order": true,
  "verbose": true
}

Phase 1: ベースライン化

  • 初期マイグレーション 1735689600000_baseline-schema.js を作成（UNIX epoch ms を接頭辞）。
  • up 内で scripts/database/ddl/schema.sql の内容を pgm.sql(fs.readFileSync(...)) で流し込む。
    注: schema.sql 自体は削除せず、ファイルロード方式で参照する（レビューしやすさと Git 差分の可視性を両立）。
  • down は「意図的に空 or DROP SCHEMA CASCADE を明示コメント付きで記述」する。 ベースラインの down は実運用で使うことはないが、記述の一貫性のために置く。
  • 既存の staging / production DB に対しては、DDL は再適用せず pgmigrations テーブルにベースラインを「適用済み」として手動 INSERT する（下記 5-3 参照）。

Phase 2: 既存ワークアラウンドのマイグレーション化

  • 1735689700000_add-shift-plans-unique-constraint.js を追加。
  • up: ops.shift_plans の unique_plan_per_store_month_type 制約を追加（重複データ検出→エラーで停止する厳密モードに）。
  • down: 制約を DROP。
  • 詳細は §6 参照。

Phase 3: 運用切替

  • scripts/database/README.md の「マイグレーション機能は使用しません」記述を更新し、新フローに置換。
  • 以降の schema 変更は「schema.sql を直接編集」ではなく「npm run db:migrate:create で新規マイグレーションを作成 → up 実行 → schema.sql を dump で再生成」に統一。
  • schema.sql は 最新スキーマの人間可読なリファレンスとして維持（真実の源はマイグレーション履歴）。

5-3. 既存環境へのベースライン適用手順（本番影響なし）

node-pg-migrate は既定で public.pgmigrations テーブルで適用履歴を管理する。 staging / production の既存 DB にはスキーマは既に存在しているため、 ベースラインマイグレーションの up を実行してはならない。 代わりに以下のいずれかで「適用済み」としてマーク: 

-- Option A: 手動 INSERT
INSERT INTO public.pgmigrations (name, run_on)
VALUES ('1735689600000_baseline-schema', NOW());

-- Option B: node-pg-migrate の --fake フラグ相当のパターン
--   (v7 系では公式サポートなし → Option A を採用推奨)

この操作は staging → production の順で shift M層が Railway Console から手動実行する。 自動化しないのは、履歴テーブルへの直接 INSERT は本質的に副作用が大きく、 レビュー可能な形で 1 回だけ実行すべきだからである。

6. 既存ワークアラウンドの扱い

backend/src/migrations/ensureShiftPlansUniqueConstraint.js（起動時実行）は、 正式マイグレーション化した後に 削除する。理由:

  • 正式マイグレーションが staging / production に適用された時点で、起動時の冪等チェックは無価値になる。
  • 起動時ロジックを残すとマイグレーションの真実の源が二重化し、混乱を招く。
  • server.js 起動シーケンスから DB スキーマ操作を切り離すことで、責務分離を明確化する。

削除タイミング

  1. 正式マイグレーション（1735689700000_add-shift-plans-unique-constraint.js）を staging に適用し検証。
  2. staging /api/health で pg_constraint に unique_plan_per_store_month_type が存在することを確認。
  3. production に適用。
  4. production 適用完了後、次の PR で ensureShiftPlansUniqueConstraint.js と server.js の呼び出しを削除。
注意: ワークアラウンドと正式マイグレーションを並存させる期間は最短にする（1 リリースサイクル以内が理想）。 並存中に本番でスキーマドリフトが再発した場合、どちらが復旧させたのかログで判別できるよう、 appendLog のメッセージにマーカーを追加すること。

7-2. ファイル命名規則

形式用途例

7-3. マイグレーションファイルのテンプレート

// 1735689700000_add-shift-plans-unique-constraint.js
export const shorthands = undefined

export async function up(pgm) {
  pgm.addConstraint('ops.shift_plans', 'unique_plan_per_store_month_type', {
    unique: ['tenant_id', 'store_id', 'plan_year', 'plan_month', 'plan_type'],
  })
}

export async function down(pgm) {
  pgm.dropConstraint('ops.shift_plans', 'unique_plan_per_store_month_type')
}

8. CI 統合設計

8-1. 目的

  1. PR に含まれるマイグレーションが クリーンな DB に対して up 実行に成功することを確認する。
  2. up → down → up の往復で冪等性を検証する。
  3. マイグレーションが schema.sql と乖離していないことを検出する（optional）。

8-2. GitHub Actions ジョブ設計

.github/workflows/ci.yml に新規ジョブ db-migration-check を追加。 既存 backend-check と並列実行する。 

  db-migration-check:
    name: DB Migration Check
    runs-on: ubuntu-latest

    services:
      postgres:
        image: postgres:15
        env:
          POSTGRES_USER: ci
          POSTGRES_PASSWORD: ci
          POSTGRES_DB: shift_scheduler_ci
        ports:
          - 5432:5432
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5

    env:
      DATABASE_URL: postgresql://ci:ci@localhost:5432/shift_scheduler_ci

    steps:
      - name: Checkout code
        uses: actions/checkout@v7

      - name: Setup Node.js
        uses: actions/setup-node@v7
        with:
          node-version: '22'
          cache: 'npm'
          cache-dependency-path: backend/package-lock.json

      - name: Install backend dependencies
        run: cd backend && npm ci

      - name: Apply all migrations (up)
        run: cd backend && npm run db:migrate:up

      - name: Verify rollback of latest migration (down + up)
        # PR で追加されたマイグレーションだけ down → up を往復させる
        run: |
          cd backend
          ADDED=$(git diff --name-only --diff-filter=A origin/${{ github.base_ref }}...HEAD \
            -- '../scripts/database/migrations/*.js' | wc -l)
          if [ "$ADDED" -gt 0 ]; then
            for i in $(seq 1 $ADDED); do
              npm run db:migrate:down
            done
            npm run db:migrate:up
          fi

      - name: Detect pending migrations (dry-run)
        run: cd backend && npm run db:migrate:status

8-3. ジョブ設計の意図

  • Postgres 15 service コンテナ: production と同じメジャーバージョン。 Railway 側の設定と揃える。
  • clean DB → up: ベースライン + 追加マイグレーションが順序通り成功することを保証。
  • PR で追加された分だけ down/up 往復: down が破壊的操作を含む場合、既存マイグレーションを巻き戻すと後続マイグレーションの前提が壊れる。 したがって PR で 新規追加された分だけロールバックを試みる。
  • --dry-run で pending 検出: CI で up 済みの状態から更に pending がある = マイグレーションを追加したのに実行漏れがある兆候。

8-4. CI 落ちのハンドリング

症状典型原因対処
up が失敗する SQL 構文エラー / 前提スキーマ不整合 ローカルで npm run db:migrate:up 再現 → 修正
down で失敗する down が未実装 or DROP 順序ミス down を実装 or 修正
dry-run で pending 検出 マイグレーションファイルの追加を忘れている ファイルを commit

8-5. Optional: schema.sql との差分検出

将来的な拡張として、CI で pg_dump --schema-only の結果と scripts/database/ddl/schema.sql の差分を検出するジョブを追加できる。 ただし PG のダンプは形式差（コメント順・引用符付与）が入りやすいため、 初期導入時はスコープ外とする。導入判断は運用開始 1 ヶ月後に見直す。

10. リスクと緩和策

リスク影響緩和策
ベースラインの pgmigrations 手動 INSERT を忘れる 本番でベースライン up が走り、既存テーブルとの重複エラーで起動失敗 デプロイ手順に明記 / staging での事前手順確認 / CREATE TABLE IF NOT EXISTS のため実害は限定的だが、事故時にエラーで気付けるよう CREATE TABLE に変更する選択肢も検討
Railway デプロイ時に自動でマイグレーションが走らない コードとスキーマが乖離、リリース後に 500 が発生 初期導入時は 手動適用とし、自動化は別 Issue で扱う（predeploy フック等の是非を含めて別途設計）
複数開発者が同時にマイグレーションを追加、タイムスタンプの前後関係と適用順序が入れ替わる DB 状態がブランチ間で非決定的になる check-order: true 設定で node-pg-migrate が起動時に検出 / PR レビューで順序確認
ワークアラウンドと正式マイグレーションの並存期間中に予期せぬ動作 起動時に既存制約を再検出、無害だが冗長ログ 並存期間を 1 リリース以内に短縮 / ログにフェーズマーカーを追加
schema.sql と実際のマイグレーション結果が乖離 新環境立ち上げ時にスキーマ不整合 マイグレーション追加時に schema.sql も同一 PR で更新するルール化（docs/ にガイド追加、CI 差分検出は将来課題）
マイグレーション失敗で production が中途半端な状態に データ整合性の破壊 node-pg-migrate は既定で 1 マイグレーション 1 トランザクション / DDL 変更を伴う PR は staging 検証必須（既存フロー）
